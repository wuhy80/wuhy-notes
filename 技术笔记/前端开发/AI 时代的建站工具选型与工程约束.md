# AI 时代的建站工具选型与工程约束

> [!summary] 一句话结论
> 做"自动搭建"工具，**AI 该生成的是配置（spec），不是代码**；前端用静态产出把客户端 JS 压到 0；后端元数据层的选择**先过许可证这一关**，技术选型排在后面。

## 1. 背景与问题

团队现有工具基于 NocoBase 做自动建站。核心疑问是：是否该换成"直接基于 Vue / React 的 AI 轻量方案"。

这个问题容易被表述成"哪个框架更好"，但实际上是三个独立问题：

1. **产物形态**：AI 产出的是代码，还是可校验的配置？
2. **前端形态**：SPA 还是静态产出？
3. **底座许可证**：能不能商业化交付？

三者中，第 3 条是唯一具有"一票否决"性质的。

## 2. 三条路线

| 路线 | 产物 | 谁解释产物 | 数据模型/迁移 | 长期维护 |
| --- | --- | --- | --- | --- |
| A 留在现有平台 | 元数据 | 平台运行时 | 现成 | 低 |
| B 底座 + 自建渲染 | 元数据 + 渲染器 | 自己的渲染器 | 现成 | 中 |
| C AI 直接生成代码 | **源码** | 浏览器 | **没有** | 高 |

C 路看着最"轻"，实际是把运维成本换成了维护成本：客户改一个字段就要重新生成组件，需求演进三次后代码库会出现三套互相打架的 CRUD 实现。v0 / Lovable / Bolt.new 这类产品就是这个形态，但它们的商业模式是**卖生成能力 + 托管**，不承诺长期自助维护。

B 路的核心判断：**把"建站"当成编译（compile），而不是生成（generate）**。

## 3. 第一道闸门：许可证

### 3.1 实测矩阵

数据来源：GitHub License API（2026-11-10）+ 仓库许可证正文。

| 方案 | 许可证标识 | 商业化交付 |
| --- | --- | --- |
| Payload | MIT | ✅ 干净 |
| JeecgBoot | Apache-2.0 | ✅ 干净 |
| Appsmith | Apache-2.0 | ✅ 干净 |
| NocoBase | 自定义 / NOASSERTION | ⚠️ 需核实商业授权 |
| Strapi · NocoDB · Baserow | 自定义 / NOASSERTION | ⚠️ 需核实 |
| Directus | MSCL-1.0-GPL | ❌ 高风险 |

### 3.2 Directus 为什么被否决

它已不是 BSL 1.1，2026 年换成 **Monospace Sustainable Core License 1.0（MSCL-1.0-GPL）**。许可证原文中的三条关键约束：

> 1. **Competing Use** = 把软件（单独或**连同你的产品/服务**）提供给第三方，并与 Licensor 自有商业版形成竞争。
> 2. **再分发限制**：不得对许可证已授予的权利收取任何许可费、版税或其他费用。
> 3. 存在 license key 门控功能，条款明确禁止绕过。
> 4. 四年后转为 GPL-3.0——对商业交付反而更不利。

对于"把 Directus 打进商业化建站工具并按客户收费"这种形态，这属于灰区偏红，除非购买商业授权。

> [!warning] 一个容易忽略的点
> **开源不等于可商用。** 大量低代码/CMS 项目用的是 BSL、SSPL、AGPL 或自定义许可。判断方法：查仓库 `/license` 返回的 `spdx_id`，凡返回 `NOASSERTION` 的，一律按"需要法务确认"处理，不要按名字想当然。

## 4. 实测：前端壳能做到多轻

用 Astro 7.4.7 + Vue 3.5.45 搭了一个"内容型官网"POC（首页 / 产品列表 / 产品详情 / 新闻详情 / 联系表单），数据全部来自统一适配层。

| 指标 | 结果 |
| --- | --- |
| 渲染器代码量 | **153 行**（Vue 组件 105 + 数据适配 48） |
| 页面数 / 构建耗时 | 7 页 / 1.1–1.4 s |
| 产物总大小 | 80.6 KiB |
| HTML 平均 | 1.26 KiB（CSS 内联，无独立 CSS 文件） |
| **客户端 JS** | **0 KiB（HTML 中 0 个 script 标签）** |
| Lighthouse Performance | **100** |
| Accessibility | 93 |
| Best Practices | 96 |
| SEO | 91 |
| LCP / TBT / CLS | 1.4 s / **0 ms** / 0.026 |

**演进测试**：新增一个 `video` 区块，改动 **2 个文件、+6 行**（渲染器 + 元数据模型），路由与页面配置零改动。

**换后端成本**：**1 个文件**——适配层内两种实现（本地 fixture / Payload REST），页面与组件不动。

### 4.1 与公开 benchmark 对照

Nolan Lawson 的 agent 框架 benchmark（2026-10）中，同形态数据：

| 指标 | 本 POC | Nolan 的 Astro | Nolan 的 Next.js |
| --- | --- | --- | --- |
| 客户端 JS | 0 KiB | 0 KiB | 142 KiB |
| TBT | 0 ms | 0 ms | 71 ms |
| Performance | 100 | 100 | 99 |

两者结论一致：**服务端/构建期出 HTML 的形态，在客户端 JS 与 TBT 上是结构性优势**，不是调优结果。

## 5. 做这种东西要注意什么

这一节是本报告的重点。以下每条都对应一个真实会踩的坑。

### 5.1 许可证与商业模型

- **先过许可证，再谈技术。** 技术选型可以返工一周，许可证问题会让整个产品下线。把"许可证核查"设为 Gate 0，没有结论不进入 POC。
- **区分三种交付形态**：SaaS 托管、私有化部署、打包进自有产品。同一份许可证对三者的约束完全不同，尤其"打包进产品收费"最容易触雷。
- **警惕定时炸弹**：BSL 类许可通常有 Change Date，到期转 GPL 后，衍生作品可能被要求开源。
- **警惕 license key 门控**：条款禁止绕过，意味着社区版能力有硬边界，交付时可能突然不够用。

### 5.2 抽象层次：生成配置，不生成代码

- **代码是不可解释的产物**：没有 schema 校验、没有 diff、没有回滚，只有"重新生成"。
- **配置才是可治理的产物**：能校验、能版本化、能灰度、能回滚。
- **AI 不许直接写数据库和权限。** 权限、多租户、审计这些"每个项目都要重写一遍"的东西，必须沉淀在元数据层，而不是每次都生成。
- **渲染器是资产，内容是产物。** 手写一次渲染器长期复用，AI 每次只生成内容。

### 5.3 渲染器的设计边界（最容易失控的地方）

> [!important] 参考教训：百度 amis
> amis 是"JSON 配置驱动 React 前端"的国内标杆，18.9k 星，但**最后提交停留在 2026-03-18**（已 8 个月）。通用 JSON 渲染器要覆盖无限场景，成本没有上限，连大厂都撑不住。

因此：

- **必须收敛**：明确支持 N 种字段类型 + M 种区块，超出边界的场景走"手写扩展"，不要试图做通用平台。
- **必须有兜底渲染**：未知区块要显式渲染成占位提示，而不是静默失败或崩页。POC 里 `.unknown` 分支就是干这个的。
- **业务逻辑不许进渲染器**：渲染器只负责"字段类型 → 组件"，任何条件、计算、权限判断都应该在数据层或配置里。
- **默认服务端渲染，客户端 JS 默认 0**：只有真正需要交互的岛才加水合，其余保持纯 HTML。

### 5.4 多站点与"可独立升级内核"

- **租户字段从第一天就要有**：即使第一个客户只有一个站点，也要在数据模型里保留 `site` 关系字段，否则第二个客户来时是灾难性改造。
- **一个实例承载 N 个站点，而不是 N 个部署**：N 个部署意味着 N 份要升级的代码。
- **"可独立升级内核"要作为唯一技术指标来设计**：代码生成派（JeecgBoot / RuoYi）结构上做不到——每个客户一份被改过的代码，升级必然冲突。这是 B 路相对它们**唯一的结构性优势**，如果这条做不到，B 路就退化成 C 路。
- **数据迁移必须版本化**：schema 变更要有迁移脚本编号，能正向执行也能回滚。

### 5.5 AI 生成层的护栏

- **生成的必须是 JSON，且过 schema 校验**：校验不过就不落地，不要"先生成再修"。
- **生成结果必须可 diff**：能看出这次改了什么，人才可能 review。
- **不要相信"某框架更适合 AI"这类结论**：公开可复现的证据极少。有 benchmark 显示元框架形态的差异远大于"库的选择"，且方差会淹没组间差异。
- **自动化检查比模型能力重要**：能被 tsc / lint / a11y 检查抓住的错误才是可接受的错误。POC 的 Accessibility 只有 93，恰恰证明"0 JS 不等于自动合规"，AI 生成的模板同样会漏 `alt`、`label`、`iframe title`。

### 5.6 合规与运维

- **留资表单涉及个人信息**：收集范围、留存期限、跨境传输需要按合规要求设计，不能由 AI 自由发挥。
- **国内站点需备案**：如果工具自动产出对外站点，备案信息、主体资质要在建站流程里前置校验。
- **静态产物也要安全头**：CSP、HSTS、X-Frame-Options 在静态托管上同样要配。
- **图片必须处理**：上传即转 AVIF/WebP + 多尺寸，否则 Lighthouse 分数会被单张原图拖垮。

## 6. 可复用的验证方法

把验证拆成四个有否决权的 Gate，避免"做完了才发现方向错"。

| Gate | 内容 | 否决条件 |
| --- | --- | --- |
| 0 | 许可证核查 | 商业化交付条款不清晰 |
| 1 | 用真实模型建 collection、权限 | 关键需求表达不了 |
| 2 | 渲染器核心实现 | 收敛不到 300 行以内 |
| 3 | 演进 + 内核升级 | 升级会破坏客户配置 |

配套的五个量化指标：

| 指标 | 定义 | 参考线 |
| --- | --- | --- |
| 渲染器代码量 | 组件 + 适配层总行数 | ≤ 300 行 |
| 客户端 JS | 首屏加载的 JS 字节 | 内容站 0 KiB |
| 演化半径 | 新增一个典型需求要改几个文件几行 | ≤ 3 文件 |
| 升级影响面 | 内核升级后需人工修改的客户配置数 | 0 |
| LCP / TBT | Lighthouse 模拟移动端 | TBT 0 ms |

## 7. 结论与下一步

1. **Directus 出局**，原因是许可证（MSCL-1.0-GPL），不是技术。
2. **前端形态成立**：Vue 渲染器 153 行、0 KiB 客户端 JS、Performance 100。
3. **"用 Vue"的诉求只能落在渲染层**：admin 层（Payload 是 React/Next）是内部使用，客户看不到。
4. **待验证**：Gate 3——N 个站点能否独立升级内核。这是 B 路成立与否的最终判据。
