# 等保 2.0 三级落地清单

> [!abstract] 定位
> 面向研发团队的等保三级实施清单：把 GB/T 22239-2019 第三级的要求，翻译成"谁、在多长时间内、做什么、怎么验收"。
> 本文是**通用模板**，不含任何具体系统的拓扑、地址和业务细节，可直接用于项目启动会与任务拆分。

---

## 0. 动手前先确认三件事

| 事项 | 结论影响 |
| --- | --- |
| **定级是否确定为三级** | 三级要专家评审 + 备案 + 每年测一次；定成二级成本差一半 |
| **部署形态** | 云上（租户责任 + 云平台扩展要求）、自建机房、私有化交付到客户机房，整改项完全不同 |
| **是否需要密评** | 涉及密码改造（国密 SM2/SM3/SM4），是整个工程里最重的一块，必须提前立项 |

> [!warning] 云上系统最常见的误解
> 「云平台过了等保」不等于「你的系统过了等保」。云厂商只对基础设施负责，**租户要对部署在云上的应用和数据单独定级、备案、测评**。迁移上云后原有机房的测评结论不能沿用。

## 1. 全流程与时间线

| 阶段 | 主要产出 | 参考周期 | 责任 |
| --- | --- | --- | --- |
| ① 定级与专家评审 | 《定级报告》、专家评审意见 | 1~2 周 | 安全/业务 |
| ② 公安备案 | 备案表、拓扑图、安全建设方案 | 2~4 周 | 安全 |
| ③ 差距评估（预测评） | 不符合项清单 + 风险分级 | 1~2 周 | 测评机构 |
| ④ 建设整改 | 技术整改 + 制度文档 | **4~8 周**（与开发并行） | 开发/运维/安全 |
| ⑤ 正式测评 | 测评报告 | 1~2 周 | 测评机构 |
| ⑥ 整改复测 | 复测报告 | 2~4 周 | 全体 |
| ⑦ 年度复测 | 每年一次 | 每年 | 安全 |

**三级系统的测评是年度强制项**，不是一次性认证。第一年把基线做进产品和流程，第二年起成本会降一个数量级。

**测评结论**分「符合 / 基本符合 / 不符合」；存在高风险不符合项时必须整改并复测。

## 2. 技术整改：五个方面

| 方面 | 主要工作 | 是否程序改造 |
| --- | --- | --- |
| 安全物理环境 | 机房门禁、温湿度、消防、供电、电磁防护、防雷 | 否（自建机房才涉及） |
| 安全通信网络 | 网络分区、带宽冗余、通信传输加密、可信通信 | 部分 |
| 安全区域边界 | 边界防护、访问控制、入侵防范、恶意代码、边界审计 | 否（安全设备） |
| **安全计算环境** | **身份鉴别、访问控制、审计、入侵防范、数据加密、备份、个人信息** | **是（核心）** |
| 安全管理中心 | 三员分立、集中管控（日志/监测/告警/补丁/运维审计） | 部分 |

## 3. 应用系统改造清单（开发主线）

优先级说明：**P0 = 高风险/必改项，不改测评必挂；P1 = 必做项；P2 = 可做替代措施或延后**。人日为参考值，按已有基础增减。

### 3.1 身份认证

| 编号 | 任务与做法 | 优先级 | 人日 |
| --- | --- | --- | --- |
| A1 | 口令策略：长度 ≥ 8（建议 12），大小写+数字+特殊字符至少 3 类，90 天更换，不与最近 5 次重复 | P0 | 3 |
| A2 | 登录失败处理：连续 5 次失败锁定账户或来源 IP，加验证码 | P0 | 2 |
| A3 | 会话管理：15 分钟无操作超时退出；登录成功后重建 SessionId；Cookie 加 HttpOnly/Secure/SameSite | P0 | 3 |
| A4 | **管理员双因素认证**：密码 + TOTP/短信/USBKey，关键操作二次确认 | P0 | 5 |
| A5 | 口令存储：bcrypt/argon2 加盐哈希，禁止明文、MD5、SHA1 | P0 | 2 |
| A6 | 默认账户处理：admin/root/guest 改名或禁用，首次登录强制改密 | P0 | 1 |
| A7 | 密码找回与重置：防枚举、令牌一次性、短有效期、重置后强制下线 | P1 | 3 |
| A8 | 全局登出与会话失效（单点登录场景） | P1 | 3 |

### 3.2 访问控制

| 编号 | 任务与做法 | 优先级 | 人日 |
| --- | --- | --- | --- |
| B1 | RBAC 权限模型 + 最小权限原则 | P1 | 5 |
| B2 | 三员分立：系统管理员 / 安全管理员 / 审计管理员权限互斥 | P1 | 3 |
| B3 | 后端强制鉴权中间件：每个接口校验，不依赖前端隐藏菜单 | P0 | 5 |
| B4 | 水平越权修复：所有按 ID 取数据的接口校验资源归属 | P0 | 8 |
| B5 | 垂直越权修复：角色校验落到服务层 | P0 | 5 |
| B6 | 账户生命周期：停用、离职回收、季度僵尸账户清理 | P1 | 2 |
| B7 | 数据分级分类 + 敏感数据访问策略（替代"强制访问控制/安全标记"，争取判部分符合） | P2 | 5 |

### 3.3 安全审计（重点）

| 编号 | 任务与做法 | 优先级 | 人日 |
| --- | --- | --- | --- |
| C1 | 统一审计事件模型：event_id、时间（NTP 同步）、用户、IP、动作、资源、结果、**before/after**、trace_id | P0 | 2 |
| C2 | 中间件全量埋点（HTTP/gRPC 拦截），保证覆盖面 | P0 | 5 |
| C3 | 关键业务显式审计（带数据变化 diff） | P0 | 5 |
| C4 | 覆盖事件：登录成功/失败、登出、改密、增删改、权限变更、配置变更、**数据导出下载** | P0 | 3 |
| C5 | 异步写本地文件（append-only、按天滚动），不阻塞业务，写失败降级告警 | P0 | 3 |
| C6 | 采集到日志平台（Filebeat/Fluent Bit → ES/Loki/云日志服务），并提供业务内查询页 | P0 | 5 |
| C7 | 防篡改：独立权限（只 INSERT）+ 每日归档到对象存储 WORM 合规保留 + 哈希链/归档哈希台账 | P0 | 3 |
| C8 | 保留策略 ≥ 180 天，且**全程在线可查**（别让冷归档卡住测评） | P0 | 1 |
| C9 | 告警规则：失败登录暴增、批量导出、权限变更、非工作时间操作 | P1 | 3 |
| C10 | meta-audit：查询审计日志的行为本身也要记录 | P1 | 1 |
| C11 | 日志脱敏：禁止记录密码、token、完整身份证/手机号 | P0 | 2 |
| C12 | 审计进程保护：不提供关闭开关，异常时关键操作 fail-closed 或强告警 | P0 | 1 |

### 3.4 输入与接口安全（入侵防范）

| 编号 | 任务与做法 | 优先级 | 人日 |
| --- | --- | --- | --- |
| D1 | 参数化查询/ORM，消除 SQL 注入 | P0 | 5 |
| D2 | 输出编码防 XSS；富文本白名单过滤 | P0 | 3 |
| D3 | CSRF 防护（Token 或 SameSite） | P1 | 2 |
| D4 | 文件上传：白名单、类型校验、重命名、隔离存储、禁止执行 | P0 | 3 |
| D5 | 排查修复 SSRF、XXE、反序列化、路径穿越 | P0 | 5 |
| D6 | 接口限流、防重放（nonce + timestamp + 签名） | P1 | 3 |
| D7 | 统一错误处理：禁止堆栈、SQL 报错、框架版本外泄 | P0 | 2 |
| D8 | 关闭调试接口：Swagger、Actuator、debug 模式、phpinfo | P0 | 1 |
| D9 | 上传文件病毒扫描（ClamAV 等） | P1 | 2 |
| D10 | 启动完整性校验（二进制哈希）+ 进程白名单，替代"可信验证" | P2 | 3 |

| 编号 | 任务与做法 | 优先级 | 人日 |

| E2 | 禁用弱协议（TLS 1.0/1.1）和弱套件 | P0 | 1 |

## 4. 主机 / 中间件 / 数据库加固

- 最小安装，关闭无用端口、服务、示例应用
- 操作系统、中间件、数据库补丁及时更新（有补丁管理记录）
- 删除或禁用默认账号，修改默认口令，禁止 root 远程直接登录
- 开启数据库审计，记录 DDL/DML 与直连操作
- 主机部署 HIDS/EDR，恶意代码库及时更新
- 配置基线核查（可使用等保基线脚本/CIS Benchmark）
- 关键主机与数据库开启双因素或堡垒机代理接入

## 5. 管理制度与执行记录（管理占约 40%）

> [!important] 最常见的失分点
> 制度文档齐全但**没有执行记录**，会被判为「有制度无落实」。管理类要求考的是"能不能拿出证据"，不是"有没有写文档"。

| 类别 | 需要的文档 | 需要的记录 |
| --- | --- | --- |
| 安全管理制度 | 制度汇编、操作规程、安全策略 | 制度发布与评审记录 |
| 安全管理机构 | 岗位职责、授权审批流程、沟通机制 | 安全会议纪要、审批单 |
| 安全管理人员 | 人员录用/离岗流程、安全协议、培训计划 | 保密协议、培训签到、离岗交接 |
| 安全建设管理 | 定级报告、建设方案、测试验收、外包管理 | 验收报告、供应商评估 |
| 安全运维管理 | 日常运维、变更、备份、应急预案、漏洞管理 | 巡检记录、变更单、备份记录、**应急演练记录**、漏洞修复台账 |

## 6. 密评专项（三级常见要求）

| 维度 | 要求 |
| --- | --- |
| 算法合规 | 使用 SM2/SM3/SM4，不用 RSA/AES/MD5 顶替 |
| 密钥管理 | 生成、存储、分发、使用、销毁全生命周期安全 |
| 方案合理性 | 密码技术用在对的地方（传输、存储、身份鉴别、完整性） |
| 产品合规 | 使用通过国家密码管理局审批的密码产品/服务 |

两个阶段：**方案评估**（建设期）+ **运行评估**（上线后，通常每年一次）。

密评会动到 TLS、签名验签、加密存储、身份认证全链路，**建议单独立项、提前 2 个月启动**。等保测评通过不代表密评通过，两者是独立评估。

## 8. 测评自查表

- [ ] 弱口令已清零，口令策略在服务端强制生效
- [ ] 管理员登录必须双因素，现场能演示
- [ ] 默认账户已改名/禁用，首次登录强制改密
- [ ] 会话 15 分钟超时，登出后 token 立即失效
- [ ] 每个接口都有后端鉴权，低权限账号打不穿高权限接口
- [ ] 修改他人资源的请求会被拒绝（水平越权已验证）
- [ ] 审计日志覆盖登录/登出/增删改/权限变更/导出
- [ ] 审计记录含 before/after，能还原"改成了什么"
- [ ] 日志保留 ≥ 180 天，且有配置截图
- [ ] 日志删不掉（权限拒绝或 WORM 锁定），能现场演示
- [ ] 查询审计日志的行为本身有记录
- [ ] 日志里没有明文密码、token、完整身份证号
- [ ] 全站 HTTPS，TLS 1.2+，无明文端口
- [ ] 敏感字段在数据库中是密文
- [ ] 密钥不在代码、配置文件和数据库中明文出现
- [ ] 有异地备份，且近半年有恢复演练记录
- [ ] 三员分立，审计管理员不归系统管理员管
- [ ] 全量服务器 NTP 同步正常
- [ ] 依赖漏洞扫描无高危未修复项
- [ ] 调试接口、错误堆栈、版本信息均不外泄
- [ ] 管理制度的每一条都有对应执行记录
- [ ] 已取得测评报告，不符合项已整改复测

## 9. 高风险项（不整改基本必挂）

1. 弱口令、默认口令未修改
2. 管理员未启用双因素认证
3. 审计日志留存不足 6 个月，或可被任意删除
4. 敏感数据（身份证、手机号、银行卡）明文存储
5. 无异地备份，或从未做过恢复演练
6. 存在可利用的越权/注入漏洞（渗透测试能打穿）
7. 未完成定级备案
8. 云上系统未做租户侧定级测评
9. 三级系统未开展密评（按行业要求）
10. 审计管理员与系统管理员为同一人

- 整改人力：主要来自自有研发，约 60~200 人日
