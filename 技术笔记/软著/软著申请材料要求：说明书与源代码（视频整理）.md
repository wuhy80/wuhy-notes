## 1. 核心认知：审查员只看两个 PDF

- 编程不是目的，**截图和两个 PDF 才是交付物**——审查员不了解也不看你真实的开发过程，只依据「使用说明书 + 源代码」这两个文件来了解软件；
- 现状：申请越来越卷，且版权中心接入了 AI 审查，过去「自动生成代码 Ctrl+A 全复制」的做法会带来**代码雷同**问题（大量重复的组件代码 + 注释，大家都这么干）；
- 因此主要精力应放在这两个文件的科学严谨性、丰富程度上，**体现出工作量**。

## 2. 使用说明书的要求

说明书分四个部分（封面 + 引言 + 总体设计 + 具体操作），配套模板见 [[软著说明书模板]]。

### 2.1 引言：三段论

1. **行业背景**：过去这个行业用什么方法解决问题，存在哪些不足、困难与不便——这是设计本软件的初衷；
2. **新方法**：本软件运用了什么新算法、新方法、新模式，能带来怎样的积极效果；
3. **具体功能**：点击哪些按钮就能实现哪些功能，且有快速响应与准确的计算结果。

### 2.2 运行环境

基本可以直接复用模板，唯一要注意：**写实际使用的版本**（如 MATLAB 版本要与实际一致）。

### 2.3 软件总体设计（技术特点）

大部分可复用模板（基于什么开发、运行占用内存小、输入参数驱动、可移植性强等），把软件具体功能替换成自己的即可。

### 2.4 软件主要功能：表述必须专业化

![[软著1-软件界面示例.png]]

- 功能名称不能简写——「相关系数计算」「模型参数计算」这种几个字了事，审查员虽然能看懂，但会**觉得软件不上档次、工作量不足、诚意不够**；
- 要从论文、课本中借用**专业化的论述方式**来描述每个功能；
- 软件界面本身在设计阶段就要「高大上」（功能面板、弹出式菜单、图表区丰富），这直接决定说明书截图的观感。

![[软著1-说明书功能列表.png]]

### 2.5 功能具体描述：加公式、加原理图

![[软著1-说明书图文标注.png]]

- 现在的要求：每个功能描述要**像写论文一样**附上计算公式、背后的原理图、模型图、涉及的知识点；
- 哪怕审查员看不懂（大概率看不懂），专业化的呈现也能提升「诚意」；
- 流程图不要用微信等聊天工具的模板画，要按自己的理解认真绘制。

### 2.6 操作说明：把审查员当小孩子教

- 一步一步演示：点哪个按钮 → 输入什么数据 → 得到什么结果；
- 截图要加**箭头**，最好加**序号标注**（推荐 QQ 截图：支持 ①②③ 步骤序号 + 弹出文字框补充「第一步点击什么按钮、输入哪些数据」），审查员能据此清楚了解运行流程；
- **输入数据必须科学严谨**：带小数点的真实量级数据，不要出现 666、123456 这类数字——会显得轻浮、不可信、降低诚意。

## 3. 源代码的要求（近年调整最大）

![[软著1-源代码格式.png]]

### 3.1 只放核心代码

- 旧做法：自动生成的代码全量复制 → 组件代码大量重复、注释冗余 → **代码雷同**风险；
- 新做法：**只保留核心代码**——各控件（弹出式菜单、pushbutton 等）callback 里自己写的功能代码（从第一行到最后一行），组件自动生成代码全部舍弃。核心代码通常 6–10 页。

### 3.2 页数与行数规则

- 版权中心要求：**超过 3000 行**提交前 30 页 + 后 30 页（每页 50 行，50×60 = 3000 行）；**少于 60 页**提交全部源代码；
- 目标页数：**50–60 页**（正好 60 页最好），太少显得工作量不足；
- **最后一行必须以 `end` 结尾**（MATLAB），没有商量余地。

### 3.3 代码量计算法（凑页数的正确姿势）

以 9 个 case、核心代码只有 6 页为例：

1. 需要补 44 页 × 50 行 = **2200 行**；
2. 2200 ÷ 9 个 case ≈ **每个 case 约 220 行**；
3. 用 DeepSeek 按此配额生成，填充到每个 case 前方，替换掉简单代码。

生成时的 prompt 模板（视频原话）：

> 我现在要用【线性回归】算法去实现【泛化误差及有限上界值参数计算】这个功能，请你用 MATLAB 语言帮我编写相应的程序，代码量在 220 行左右。

要点：

- **多用不同算法**：线性回归、逻辑回归、神经网络、强化学习等约十类智能算法——9 个 case 用 9 种不同的算法，既真实又避免雷同；
- 生成后删掉空行、单独占行的多余 `%` 注释行。

### 3.4 中文注释对齐说明书（关键技巧）

![[软著1-源代码case注释.png]]

- 审查员**不是计算机专业**，看不懂运行逻辑，只能看整体结构；
- 在每个 case 前加中文注释（`%` 行），内容直接**从使用说明书里复制对应的操作表述**——「点击什么按钮，根据什么参数，就能得到什么数值」；
- 审查员据此把源代码里的 case 与说明书里的功能**一一比对**，确认一致 → 不会判定代码与说明书偏离 → **不会出现补正**。

## 4. 风险与边界

> [!warning] 不要大肆传播
> UP 主明确说：这套方法是实践验证过的最新审核方向，但一旦传播开、大家都这么写，版权中心的审查策略会相应调整，届时下证难度又会提高。做好自己的事就好。

## 5. 可复用的经验

> [!tip] 材料自查清单
> - [ ] 说明书四部分齐全：封面、引言（三段论）、总体设计、功能具体描述与操作说明
> - [ ] 引言是否覆盖「过去的不足 → 新方法 → 具体功能」
> - [ ] 每个功能是否有专业化表述（论文式），而非一句话
> - [ ] 功能描述是否附了公式、原理图、流程图
> - [ ] 操作截图是否带箭头和序号标注
> - [ ] 示例数据是否科学严谨（小数点、真实量级）
> - [ ] 源代码是否只含核心代码（无组件自动生成代码）
> - [ ] 页数是否在 50–60 页、每页约 50 行
> - [ ] 最后一行是否以 `end` 结尾
> - [ ] 每个 case 是否有对齐说明书的中文注释
> - [ ] 算法是否多样化（避免与他人雷同）
