# 软著申请方案

> [!abstract] 定位
> 综合两个视频的实战经验（[[软著申请材料要求：说明书与源代码（视频整理）|材料要求]]、[[软著申请路线：AI 生成与自建对比（视频整理）|路线对比]]）与本库已有资产（[[软著说明书模板]]、`scripts/generate-software-doc.js` 自动截图生成脚本），沉淀一套可复用的软著申请工作流。

---

## 0. 路线决策（先选路，再干活）

| 情形 | 推荐路线 |
| --- | --- |
| 材料要经得起答辩/审计，或软件本身要真用 | **DIY + AI 辅助**（本方案主体） |
| 急着下证、无人审核、追求效率 | AI 一键生成（智著引擎 99 元/份，界面质量高） |
| 企业资质申报、批量走量 | AI 生成（Best 软著 30 元/份，海投换确定性） |

本方案按**质量优先的 DIY + AI 辅助**路线展开；若选 AI 代生成，重点做最后的「质量自查」环节。

## 1. 材料清单

| 材料 | 说明 |
| --- | --- |
| 软件著作权登记申请表 | 官方系统在线填写；软件全称、版本号（V1.0）、开发完成日期等 |
| **使用说明书**（文档鉴别材料） | Word/PDF，图文并茂；审查员看的第一个文件 |
| **源代码**（程序鉴别材料） | 前 30 页 + 后 30 页（超 3000 行时）或全部（不足 60 页时） |
| （可选）可运行软件包 | 用于单位内部演示、应对核查 |

## 2. 说明书制作规范

结构：**封面 → 一、引言 → 运行环境 → 二、软件总体设计 → 软件主要功能 → 功能具体描述 → 三、操作说明**，格式细节（页边距 2.5cm、1.5 倍行距、黑体标题/宋体正文等）直接照 [[软著说明书模板]] 执行。

### 2.1 内容要求

1. **引言三段论**：过去的不足（行业背景）→ 本软件的新算法/新方法与积极效果 → 具体功能概述；
2. **运行环境**：可复用模板，但版本号写实际使用的；
3. **技术特点**：可复用模板骨架，替换为本次软件的真实功能；
4. **功能表述专业化**：从论文/课本借用论述方式，禁止一句话功能（"相关系数计算"这类）；
5. **功能描述加料**：每个功能附**计算公式 + 原理图/流程图**，像写论文一样；
6. **操作说明**：把审查员当新手，一步一图；截图加箭头 + ①②③ 序号标注（QQ 截图支持步骤序号 + 文字框）；
7. **示例数据严谨**：带小数点、真实量级，严禁 666 / 123456 这类数字。

### 2.2 自动化产线（本库已有）

- `scripts/generate-software-doc.js`：Puppeteer 自动登录目标系统（凭据走环境变量 `SOFTDOC_URL / SOFTDOC_USER / SOFTDOC_PASS`）→ 按 1920×1080 自动截图到 `软著截图/` → 用 docx 库生成 `软著说明书.docx`；
- 配套入口：`scripts/run-software-doc.sh`；
- 截图要求（模板已定）：1920×1080、含地址栏与标题栏、PNG/JPG ≤500KB、宽度 14–16cm；
- 流程：**先在界面上按功能菜单顺序走一遍操作脚本 → 自动截图 → 按 [[软著说明书模板]] 的截图清单插入文档 → 补公式与原理图 → 人工通读润色**。

## 3. 源代码制作规范

1. **只放核心代码**：各控件 callback 内自己实现的功能代码；框架自动生成的组件代码全部剔除（防代码雷同）；
2. **页数目标 50–60 页、每页 50 行**：超 3000 行交前后各 30 页；不足 60 页交全部；
3. **最后一行必须 `end` 结尾**（MATLAB）；
4. **代码量配额法**：（目标行数 − 现有行数）÷ 功能 case 数 = 每个 case 的生成行数（如 220 行），逐个让 DeepSeek 生成并填充；
5. **算法多样化**：十类智能算法（线性/逻辑回归、神经网络、强化学习等）尽量不重样，既显真实又降低雷同率；
6. **中文注释对齐**：每个功能块开头加 `%` 中文注释，内容从说明书的对应操作表述复制——审查员据此逐条比对说明书与代码，对齐了就不会有补正；
7. 删除空行、整行的单独 `%`。

> [!note] 生成模板句式
> 「我现在要用【某算法】实现【某功能】，请用【语言】编写相应程序，代码量约【N】行。」——功能名与说明书表述保持一字不差。

## 4. 提交前质量自查

- [ ] 两个 PDF（说明书 + 源代码）通读一遍，功能名称逐字一致
- [ ] 说明书：公式、原理图、流程图齐全；截图有箭头序号；数据真实
- [ ] 源代码：无组件生成代码残留、无空行、末行 `end`
- [ ] 说明书功能 ↔ 源代码 case 一一对应
- [ ] 与他人材料对比无雷同（尤其用同一模板/服务的同伴）
- [ ] 版本号、日期、名称在申请表、说明书、源代码页眉三处一致

## 5. 风险与边界

> [!warning] 三条红线
> 1. **不要买/抄现成材料**：有真实案例因界面雷同被同学举报，学校现场查验运行 + 逐行答辩翻车；
> 2. **不要互相传播模板化技巧**：都一样写，审查策略就会收紧；
> 3. **测评/审查标准会变**：本方案基于 2026 年的实践验证，提交前留意版权中心最新公告。

## 6. AI 参与的边界：能做什么、不能做什么

结合两个视频的实测信息与登记制度本身的要求，AI 参与「软著申请」可以分三层看：

### 6.1 AI 辅助真实软件（✅ 推荐且完全没问题）

软件**真实存在、由申请人（团队）开发**，AI 只作为工具：

- 专业化措辞润色、公式与原理解释、说明书按模板排版；
- 给真实功能补算法实现、生成中文注释、凑源代码页数的配额生成；
- 自动截图产线（本库 `generate-software-doc.js`）。

这相当于用编译器和脚手架，创作主体仍是人，登记材料与开发事实一致——下证率高（视频实测 DIY+AI 约 90%），答辩、核查、维权都站得住。

### 6.2 AI 大幅扩写薄软件（⚠️ 灰色，看用途）

软件真实但功能较薄，用 AI 大量扩充功能描述、生成与实际关联弱的代码去「增重」。下证概率尚可，但材料与实际软件的偏离在答辩、单位核查、高新资质抽查时会暴露；自己要想清楚用途再决定。

### 6.3 AI 凭空生成虚拟软件（❌ 不建议）

软件不存在，直接买/生成「全套源码+说明书+界面」去申报（视频里的 30/99 元服务本质是这类，靠走量赌下证率）。风险不只是被驳回：

- **合规**：登记的软件与开发事实不符属虚假申报，证书存在被撤销的先例机制；用于高新技术企业等资质申报一旦被抽查，后果远超一张证书；
- **权属**：纯 AI 生成、无真实开发的「软件」，著作权权属本身存疑，证书在真实维权中价值有限；
- **现实**：版权中心已接入 AI 审查，同一批生成服务的产物特征明显（界面大差不差、组件代码重复），雷同是主要拦截点；视频里就有被同学举报、现场运行+逐行答辩翻车的真实案例；
- **经济**：所谓「三中一」意味着反复重交补正，时间成本未必比真做低。

> [!important] 一句话判断标准
> **软件是真的，AI 只是工具 → 可以且推荐；软件是编的，AI 是原料 → 别做。**
> 若动机是单位资质走量，更稳妥的路是把团队每年真实产生的小工具、内部系统批量整理申软著——真实在用的软件远比想象的多，根本不需要编。
