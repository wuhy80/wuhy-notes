在使用 kubeadm 安装的 Kubernetes 1.24 版本集群中，etcd 通常是作为集群的一部分，并且每个 Master 节点都会运行一个 etcd 实例，形成一个 etcd 集群。这种配置下，etcd 本身是高可用的，因为它有多个副本，但并不意味着 etcd 是通过外部负载均衡器运行的。相反，etcd 集群内部通过选举机制来确保高可用性。

要检查 etcd 是否高可用以及整个 Kubernetes 集群是否高可用，你可以执行以下步骤：

# 检查 etcd 高可用性
1. **登录到任意一个 Master 节点**：
由于每个 Master 节点都运行一个 etcd 实例，你可以登录到任意一个 Master 节点进行检查。

添加 alias，将下面的内容放到/etc/profile 中，然后 source /etc/profile 生效
```bash
alias etcdctl="ETCDCTL_API=3 etcdctl --endpoints=https://<master-node-ip>:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key"
```
2. **检查 etcd 成员状态**：
使用 etcdctl 工具来检查 etcd 集群的成员状态：
```bash
etcdctl member list
```
将 `<master-node-ip>` 替换为任意一个 Master 节点的 IP 地址。你应该看到多个成员，每个成员对应一个 Master 节点。
![image.png](https://wuhy-1258420163.cos.ap-shanghai.myqcloud.com/obsidian/images/2024/group_1/202405091012874.png)

3. **检查集群健康状态**：
使用以下命令检查 etcd 集群的健康状态：
```bash
etcdctl endpoint health
```
如果集群健康，输出应该显示所有成员都是健康的。
![image.png](https://wuhy-1258420163.cos.ap-shanghai.myqcloud.com/obsidian/images/2024/group_1/202405091014531.png)

# 检查 Kubernetes 集群高可用性
1. **检查 API 服务器状态**：
使用以下命令检查 API 服务器的状态：
```bash
kubectl get componentstatuses
```
你应该看到所有Master节点的状态都是 `Healthy`。

2. **检查控制平面组件**：
检查控制平面组件（如 kube-apiserver、kube-controller-manager、kube-scheduler）是否在所有 Master 节点上运行：
```bash
kubectl get pods -n kube-system -o wide
```
你应该看到这些组件的多个副本在不同的 Master 节点上运行。

3. **检查工作节点状态**：
使用以下命令检查所有工作节点（Node）的状态：
```bash
kubectl get nodes
```
所有工作节点都应该处于 `Ready` 状态。

# 如何更新 config 文件

在Kubernetes集群中，`/etc/kubernetes/admin.conf` 文件是用于配置kubectl命令行工具的kubeconfig文件。这个文件包含了访问集群的必要信息，如API服务器的地址、客户端证书、私钥和CA证书等。当你在每个Master节点上查看这个文件时，你可能会发现它们都指向了同一个API服务器地址，例如 `https://192.0.2.201:6443`。

这种情况通常是因为在初始设置时，集群的第一个Master节点（在这个例子中是 `192.0.2.201`）被配置为默认的 API 服务器地址。在多 Master 集群中，每个 Master 节点都会运行一个 kube-apiserver 实例，但 kubeconfig 文件通常只包含一个 API 服务器的地址。

如果集群中的某个Master节点（例如`192.0.2.201`）发生故障，集群仍然可以正常工作，前提是其他Master节点上的kube-apiserver实例能够接管服务。为了确保这一点，你需要：
1. **内部负载均衡**：确保集群内部有某种形式的负载均衡机制，如kube-proxy的iptables或IPVS规则，可以将流量分发到所有可用的kube-apiserver实例。这样，即使一个节点失败，流量也可以被重定向到其他健康的节点。
2. **DNS或服务发现**：使用DNS记录或服务发现机制来动态更新API服务器的地址。这样，客户端可以自动发现并连接到可用的kube-apiserver实例。
3. **kubeconfig更新**：如果`192.0.2.201`节点永久性故障，你需要更新所有kubeconfig文件，将API服务器的地址更改为其他可用的Master节点地址。
4. **控制平面组件**：确保kube-controller-manager和kube-scheduler等控制平面组件能够在多个Master节点之间进行故障转移。这些组件通常通过选举机制来确定主节点，并在主节点失败时自动进行故障转移。
5. **etcd集群**：确保etcd集群是高可用的，并且所有Master节点都能够与etcd集群通信。etcd集群的健康状况直接影响到整个Kubernetes集群的健康状况。

总之，即使 `/etc/kubernetes/admin.conf` 文件中的API服务器地址指向了特定的Master节点，只要集群内部有适当的负载均衡和故障转移机制，集群就可以在单个Master节点故障时继续正常工作。如果需要，你应该更新kubeconfig文件以反映当前可用的API服务器地址。

# 不使用外部负载均衡的缺点
如果不配置外部负载均衡器，当某个Master节点异常时，手动修改kubeconfig文件中的API服务器地址（`server` 字段）确实是一种临时的解决方案，可以让你的 `kubectl` 客户端继续连接到集群。然而，这种方法有几个潜在的问题和限制：

1. **手动干预**：每次 Master 节点发生故障时，都需要手动更新 kubeconfig 文件，这不仅繁琐，而且容易出错。
2. **高可用性问题**：如果集群没有配置为高可用，那么只有一个 Master 节点作为 API 服务器，这意味着集群的控制平面没有冗余。如果这个唯一的 Master 节点发生故障，集群将无法正常工作，直到你手动更新 kubeconfig 文件。
3. **网络配置**：如果集群中的其他组件（如 kubelet、kube-proxy 等）也依赖于 kubeconfig 文件中的 API 服务器地址，那么它们也需要更新以指向新的 Master 节点。
4. **自动化和弹性**：手动更新 kubeconfig 文件不支持自动化和弹性。在生产环境中，通常需要更自动化的解决方案来处理 Master 节点的故障转移。
5. **DNS 或服务发现**：理想情况下，应该使用 DNS 或服务发现机制来自动更新 API 服务器的地址。这样，客户端可以自动发现并连接到可用的 kube-apiserver 实例，而不需要手动更新 kubeconfig 文件。

### 替代方案
- **内部负载均衡**：在多 Master 节点集群中，可以使用内部负载均衡器（如 kube-proxy 的 IPVS 或 iptables 规则）来分发对 kube-apiserver 的请求。这样，即使某个 Master 节点发生故障，内部负载均衡器也可以将流量重定向到其他健康的节点。
- **DNS 轮询**：配置 DNS 服务器以轮询方式将请求分发到多个 Master 节点的 IP 地址。这样，客户端可以通过 DNS 名称而不是单个 IP 地址来访问 API 服务器。
- **服务发现**：使用服务发现工具（如 Consul、Etcd 或 ZooKeeper）来动态发现可用的 API 服务器地址。
- **自动化脚本**：编写自动化脚本，在检测到 Master 节点故障时自动更新 kubeconfig 文件。

总之，虽然手动修改 kubeconfig 文件可以作为一种临时的应急措施，但它不是实现高可用性的最佳实践。在生产环境中，应该考虑使用外部或内部负载均衡器、DNS 轮询、服务发现或其他自动化解决方案来确保集群的稳定性和弹性。

# 如何检查是否内部均衡
要确定 Kubernetes 集群是否使用内部负载均衡的方式来分发对 kube-apiserver 的请求，你可以检查集群的网络配置和 kube-proxy 的设置。以下是一些方法来验证集群是否使用了内部负载均衡：

### 方法 1: 检查 kube-proxy 模式

kube-proxy是Kubernetes集群中的网络代理，它负责将流量转发到正确的服务后端。kube-proxy可以配置为使用不同的模式，包括 `iptables`、`ipvs` 或 `userspace`。其中，`ipvs` 和 `iptables` 模式可以实现内部负载均衡。

1. 登录到集群中的一个节点（可以是工作节点或 Master 节点）。
2. 使用以下命令检查 kube-proxy 的配置：
```bash
kubectl get configmap -n kube-system kube-proxy -o yaml|grep mode
```
这将显示kube-proxy容器的命令行参数。它应该设置为 `ipvs` 或 `iptables`。
```bash
mode: ipvs
```
或
```bash
mode: iptables
```
如果 `--proxy-mode` 设置为 `ipvs` 或 `iptables`，则表示 kube-proxy 正在使用内部负载均衡。

### 方法 2: 检查 iptables 规则
如果kube-proxy使用 `iptables` 模式，你可以检查节点上的 iptables 规则来查看是否存在指向 kube-apiserver 的负载均衡规则。
1. 登录到集群中的一个节点。
2. 使用以下命令列出所有的 iptables 规则：
```bash
iptables-save
```
查找类似以下的规则，这些规则将流量重定向到 kube-apiserver 的多个实例：
```bash
-A KUBE-SVC-XXXX -m comment --comment "default/kubernetes:" -j KUBE-SEP-YYYY
```
这里的 `KUBE-SVC-XXXX` 是一个服务链（chain），而 `KUBE-SEP-YYYY` 是一个后端服务端点（endpoint）链。如果存在多个这样的规则，并且它们按照一定的概率分布来分发流量，那么这表明使用了内部负载均衡。

### 方法 3: 检查 IPVS 规则
如果kube-proxy使用 `ipvs` 模式，你可以检查节点上的 IPVS 规则来查看是否存在指向 kube-apiserver 的负载均衡规则。
1. 登录到集群中的一个节点。
2. 使用以下命令列出所有的 IPVS 规则：
```bash
ipvsadm -Ln
```
查找类似以下的条目，这些条目显示了 kube-apiserver 服务的虚拟服务器和真实服务器（后端实例）：
```bash
IP Virtual Server version 1.2.1 (size=4096)
Prot LocalAddress:Port Scheduler Flags
  -> RemoteAddress:Port           Forward Weight ActiveConn InActConn
TCP  10.96.0.1:443 rr
  -> 10.240.0.10:6443            Masq    1      0          0
  -> 10.240.0.11:6443            Masq    1      0          0
  -> 10.240.0.12:6443            Masq    1      0          0
```
这里的 `10.96.0.1:443` 是虚拟服务器的地址和端口，而 `10.240.0.10:6443`、`10.240.0.11:6443` 和 `10.240.0.12:6443` 是后端 kube-apiserver 实例的地址和端口。如果存在多个后端实例，并且使用了轮询（rr）或其他调度算法，那么这表明使用了内部负载均衡。
![image.png](https://wuhy-1258420163.cos.ap-shanghai.myqcloud.com/obsidian/images/2024/group_1/202405091059916.png)
通过以上方法，你可以验证 Kubernetes 集群是否使用了内部负载均衡来分发对 kube-apiserver 的请求。如果集群使用了内部负载均衡，你应该能够看到相应的 kube-proxy 模式设置、iptables 规则或 IPVS 规则。

# 检查负载均衡器配置（如果适用）

如果你的集群配置了外部负载均衡器来分发 API 服务器的流量，确保负载均衡器正确地将流量分发到所有 Master 节点。这通常涉及到查看负载均衡器的管理界面或配置文件，以确保所有 Master 节点都被正确地添加到了负载均衡池中。

### 注意事项

- 确保你有足够的权限来执行上述检查。
- 如果你使用的是 kubeadm 安装的集群，通常不需要外部负载均衡器来管理 etcd，因为 etcd 集群内部已经实现了高可用性。
- 在执行任何检查之前，确保你的 etcd 客户端工具（如 etcdctl）与你的 etcd 集群版本兼容。

通过上述步骤，你应该能够检查 etcd 是否高可用以及整个 Kubernetes 集群是否高可用。如果你遇到任何问题，可能需要查看 etcd 和 Kubernetes 组件的日志，或联系你的 Kubernetes 集群管理员。
