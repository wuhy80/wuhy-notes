Q: 我不要加外部的负载均衡器，只要在集群内部是高可用的。可以默认都指向master-one，然后等master-one出问题再修改各个节点的config文件指向另外一个手动指定的节点，只要保证etcd是高可用的应该就可以

根据您的需求，您希望将单节点的Kubernetes集群改造为高可用集群，但不使用外部负载均衡器，而是通过集群内部实现高可用性。具体要求是默认情况下所有节点指向 `master-one`，在 `master-one` 出现问题时手动修改各个节点的配置文件指向另一个节点，同时确保 `etcd` 是高可用的。以下是针对此需求的完整分析和实现步骤。

---

## **实现高可用集群的方案**

### **1. 部署多个控制平面节点**
为了实现高可用性，需要在集群中部署多个控制平面节点，即使不使用外部负载均衡器，多个控制平面节点也能提供冗余。

- **步骤**：
  1. 假设当前有一个单节点（`master-one`），使用`kubeadm`初始化了集群。
  2. 添加至少两个新的控制平面节点（例如`master-two`和`master-three`）。
  3. 在新节点上运行`kubeadm join --control-plane`，将其加入集群并部署控制平面组件（API Server、Controller Manager、Scheduler）。
     ```bash
     kubeadm join <master-one-ip>:6443 --token <token> --discovery-token-ca-cert-hash <hash> --control-plane
     ```
  4. 完成后，集群将有多个控制平面节点。

- **结果**：控制平面组件在多个节点上运行，具备冗余能力。

---

### **2. 配置etcd高可用性**
`etcd`是Kubernetes的关键组件，负责存储集群的状态和配置数据。确保`etcd`高可用是实现高可用集群的核心要求。

- **步骤**：
  1. 使用`kubeadm`默认的堆叠式拓扑（stacked topology），在每个控制平面节点上运行一个`etcd`实例。
  2. `kubeadm`会自动将这些`etcd`实例配置为一个高可用的`etcd`集群。
  3. 验证`etcd`集群状态：
     ```bash
     kubectl get pods -n kube-system | grep etcd
     ```
     确保每个控制平面节点上都有一个`etcd`实例运行。

- **结果**：`etcd`集群分布在多个节点上，即使某个节点（如`master-one`）故障，`etcd`仍能正常工作，保证集群数据的高可用性。

---

### **3. 默认指向`master-one`并手动切换**
按照您的要求，默认情况下所有节点都指向`master-one`，在`master-one`故障时手动修改配置指向另一个节点。

- **默认配置**：
  - 在所有节点（包括工作节点）的`/var/lib/kubelet/kubeconfig`文件中，将API服务器地址设置为`master-one`的地址：
    ```yaml
    server: https://<master-one-ip>:6443
    ```
  - 确保集群初始化时，`master-one`的地址被用作默认的API服务器地址。

- **手动切换**：
  1. 当`master-one`出现故障时，选择一个健康的控制平面节点（例如`master-two`）。
  2. 在所有节点的`/var/lib/kubelet/kubeconfig`文件中，将API服务器地址修改为`master-two`：
     ```yaml
     server: https://<master-two-ip>:6443
     ```
  3. 重启每个节点的`kubelet`服务：
     ```bash
     systemctl restart kubelet
     ```
  4. 验证集群状态：
     ```bash
     kubectl get nodes
     ```

- **注意**：
  - 手动修改配置需要逐个更新所有节点的`kubeconfig`文件，操作较繁琐。
  - 在切换完成前，集群可能会有短暂不可用时间。

---

## **方案验证**
- **控制平面高可用**：多个控制平面节点确保即使`master-one`故障，其他节点仍可接管。
- **etcd高可用**：`etcd`集群分布在多个节点，保证数据一致性和可用性。
- **手动切换**：通过修改`kubeconfig`实现从`master-one`到其他节点的切换。

---

## **局限性与建议**
- **服务中断时间**：手动切换需要人工干预，可能导致服务中断时间较长（取决于操作速度）。
- **操作复杂性**：在故障时需要快速准确地修改所有节点的配置，存在一定操作风险。
- **改进建议**：虽然您不希望使用外部负载均衡器，可以考虑在集群内部部署类似[MetalLB](https://metallb.universe.tf/)的解决方案，提供自动故障转移功能，减少手动操作的复杂性和中断时间。

---

## **总结**
按照您的要求，不使用外部负载均衡器，通过以下方式可以在集群内部实现高可用性：
1. 部署多个控制平面节点，提供控制平面组件的冗余。
2. 配置高可用的`etcd`集群，确保数据存储的可靠性。
3. 默认所有节点指向`master-one`，在故障时手动修改`kubeconfig`文件切换到其他节点。

此方案能够满足您的需求，确保`etcd`高可用，同时通过手动切换实现控制平面的故障转移。如需更详细的操作指导，可参考[Kubernetes官方文档](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/high-availability/)。
