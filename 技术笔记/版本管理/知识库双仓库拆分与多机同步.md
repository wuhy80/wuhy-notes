# 知识库双仓库拆分与多机同步

> [!summary] 一句话
> 2026-10-01 把原知识库拆成两个**独立且都私有**的 git 仓库：**主库**（技术/学习/项目）与**私密库**（私密资料 + 日记 + 任务），用 `git filter-repo` 把私密路径从主库历史中彻底剥离；并改用**独立备份脚本 + 计划任务**替代已经失效的 obsidian-git 自动备份。

## 一、拆分结果

| 仓库 | 路径 | 内容 |
|---|---|---|
| **主库** | `E:\Obsidian\wuhy80_new` | 技术笔记、大模型、读书笔记、极客时间、编程语言、专项项目（不含客户档案）等 |
| **私密库** | `E:\Obsidian\wuhy80_private` | 我的日记、个人信息、投资管理、专项项目/客户档案信息、任务管理、Inbox、网址收藏/账号信息.md |
| **回退镜像** | `E:\Obsidian\_backup_vault_before_split.git` | 拆分前的完整镜像（1218 提交 / 256.6 MB），出问题可从它恢复 |

| 指标 | 主库 | 私密库 |
|---|---|---|
| 提交数 | 603（拆分前 1218） | 864 |
| 跟踪文件 | 834（拆分前 1371） | 550 |
| 仓库体积 | 243.3 MB | 1.7 MB |

剥离后主库历史中**已检索不到**任何私密路径（`git log --all -- <路径>` 全部为空）。

> [!warning] filter-repo 的副作用
> 改写历史时它会**移除所有远程，并抹掉 `branch.*.remote/merge` 上游配置**。所以拆分后必须手动补回：远程地址、per-remote 的 push refspec、以及上游跟踪，否则 `git push` 会报 "no upstream branch"。

## 二、私密库的约定

- 私密库是**独立的 Obsidian vault**：在 Obsidian 里「打开文件夹作为库」选 `E:\Obsidian\wuhy80_private`
- 已复制 `.obsidian/`（25 个插件）与 `template/`（含日志、周报、月报、年报模板），**日记工作流开箱可用**：Daily Notes、Periodic Notes、Templater 的路径均验证可解析
- `.obsidian/` **不纳入版本控制**（与主库策略一致，避免插件内的密钥进入仓库）
- 日记、周报、月报、年报都在这个库里，相对路径与拆分前完全一致

## 三、自动备份机制（已替换）

> [!danger] 原自动备份失效的根因
> **`obsidian-git` 插件已经被卸载**，不是配置错误：
> - `.obsidian/community-plugins.json` 的 25 个插件里没有它
> - `.obsidian/plugins/obsidian-git/` 目录不存在
>
> 这正好解释了为什么最后一条自动备份提交停在 **2025-04-11**。

现在改用不依赖 Obsidian 的方案：

| 项目 | 内容 |
|---|---|
| 脚本 | `E:\Obsidian\wuhy80_new\scripts\backup-vaults.ps1` |
| 日志 | `E:\Obsidian\_backup\backup.log`（超过 1 MB 自动轮转为 `.log.1`） |
| 计划任务 | `ObsidianVaultBackup`，**每 30 分钟 + 每次登录**触发 |
| 行为 | 对两个库依次 `git add -A` → 有改动则提交 → 对每个远程重试推送 2 次并记录结果 |
| 推送映射 | 两库 `github` 设 `remote.github.push = refs/heads/master:refs/heads/main`；主库 `origin` 设 `refs/heads/master:refs/heads/master`。显式 refspec 让 `git push <remote>` 不再依赖 upstream |
| 合并保护 | 检测到 `.git/MERGE_HEAD` 或 `.git/rebase-merge` 时跳过本次提交 |
| 私密库说明 | 私密库根目录有 `README.md`，写明内容、备份方式与「必须保持私有」 |

手动执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Obsidian\wuhy80_new\scripts\backup-vaults.ps1
Get-Content E:\Obsidian\_backup\backup.log -Tail 20
```

管理计划任务：

```powershell
Get-ScheduledTask -TaskName ObsidianVaultBackup | Select TaskName, State
Start-ScheduledTask  -TaskName ObsidianVaultBackup     # 立即跑一次
Unregister-ScheduledTask -TaskName ObsidianVaultBackup -Confirm:$false   # 卸载
```

> [!important] 脚本必须禁止凭据交互
> 脚本开头设置了 `GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=never`。**去掉这几行会让脚本永久挂起**——第一次试跑就卡在 `git push` 等待 Gitea 密码上，十分钟没返回。

## 四、推送到 GitHub（本机网络注意）

本机访问 GitHub 的实测特点：

- `github.com` 的 HTTPS **时通时断**（曾连续 3 次 21 秒超时）
- `raw.githubusercontent.com` **被重置**，下载 raw/zip 需走 `gh-proxy.com` 之类的加速前缀
- **SSH 稳定可用**（22 和 443 都通），已配置走 443：

```
Host github.com
  HostName ssh.github.com
  Port 443
  User git
  IdentityFile C:\Users\Administrator\.ssh\id_ed25519
  IdentitiesOnly yes
  ServerAliveInterval 30
  ServerAliveCountMax 6
```

两个目标仓库首次推送时远端只有一条无关的「初始化」提交，因此需要 `--force`：

```bash
git push --force github master:main
```

主库体积 243 MB，链路抖动时用**分段推送**降低重试成本。已经写成脚本，配好凭据后一条命令搞定：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File E:\Obsidian\wuhy80_new\scripts\first-push-to-github.ps1
```

脚本流程：SSH 认证前置检查 → 先推私密库（1.7 MB）验证链路 → 主库取历史中点先推一次 → 再推 HEAD（增量）→ 核对远程分支。每次推送最多重试 5 次、间隔 10 秒；认证不可用会直接退出并提示。

## 五、家里那台机器的对齐（关键步骤）

> [!danger] 顺序绝对不能颠倒
> 主库历史已被改写。家里那台如果直接 `git fetch && git reset --hard`，会**把工作区里的私密文件一并删掉**（因为它们在旧历史里被跟踪，在新历史里不存在）。

1. **先在家里那台**把私密内容整体复制出去（U 盘、网盘或任意临时目录）：
   - `我的日记/`、`个人信息/`、`投资管理/`、`专项项目/客户档案信息/`、`任务管理/`、`Inbox/`、`网址收藏/账号信息.md`
2. 复制完成并确认无误后，再对齐主库：
   ```bash
   cd <主库路径>
   git fetch origin
   git reset --hard origin/master
   ```
3. 把第 1 步复制出来的私密内容，放进家里那台的**私密库**目录（`git clone` 出来的 `wuhy80_private`），逐项比对确认后提交
4. 家里那台如果还在跑 obsidian-git，**建议一并卸载**，改用同一份 `backup-vaults.ps1`（脚本对路径不敏感，两个库都在就跑两个）

## 六、其他遗留事项

- 主库的 `.obsidian/daily-notes.json` 与 `periodic-notes/data.json` **仍指向 `我的日记/`**。在主库按 `Ctrl+D` 会重新创建该目录，而它已被 `.gitignore` 排除——**会被静默地排除在备份之外**。日记请一律在私密库里记录。
- 主库 `.gitignore` 中保留着私密路径的排除规则。目录虽已不存在，但规则留下可作保险：万一将来误建同名目录，不会被提交。
- Gitea（`origin`）里的主库仍是改写前的历史，需要 `--force` 覆盖。**在此之前，家里那台不要从 Gitea 拉取**。
- **工具脚本写文件务必不要带 BOM**：PowerShell 的 `Set-Content -Encoding utf8` 在本机会写出 BOM，已因此踩坑两次——`filter-repo` 的路径清单首行失效（导致最敏感的 `个人信息/` 漏迁），以及 GitHub API 创建仓库返回 400（"Problems parsing JSON"）。可靠写法：
  ```powershell
  [System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))
  ```
