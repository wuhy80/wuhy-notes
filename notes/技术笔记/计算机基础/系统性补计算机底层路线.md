# 系统性补计算机底层：一条可验收的路线

> [!abstract] 这份路线怎么用
> 面向「有多年工程经验、但底层是黑盒」的人，不是科班课表。排序原则是 **ROI 从高到低**，而不是「教科书从下往上」。每一层都给了**可运行的产出**和**能回答的问题**——答不出来就是没学会，别看下一层。

## 为什么不从数字电路开始

很多"补底层"清单会让你先学数电、再学组成原理、再学汇编——这是**培养体系**的顺序，不是**补短板**的顺序。

工程人补底层的真实痛点是这些：

- 程序崩了，只知道"段错误"，说不出是哪个指针越界
- 服务慢了，只会加机器，说不出是 CPU-bound 还是 memory-bound
- 依赖冲突，只会删 `node_modules`，说不出 ELF 的符号解析和重定位在干什么
- 看反汇编一片茫然，`lea` 和 `mov` 都分不清
- 同事讲 `futex`、`TLB`、`false sharing`，只能点头

这些痛点全部集中在 **台阶 1~4**。数字电路和 CPU 微架构属于"想懂根"的加分项，放在最后，随时可以砍。

> [!tip] 一句话
> 先打通「源码 → 机器码 → 进程 → 内核」这条竖线，再回头补横向的硬件细节。

## 一张地图

```
你的程序
  ↓  语言运行时 / 标准库
编译器 (前端 → IR → 后端)
  ↓  汇编文本
汇编器 → 目标文件 (.o / .obj)
  ↓  符号表 + 重定位
链接器 → 可执行文件 (ELF / PE)
  ↓  加载器映射地址空间
进程 / 线程
  ↓  ABI + 系统调用
内核 (调度 / 内存管理 / 文件系统 / 网络栈)
  ↓  驱动
硬件 (CPU 流水线 / 缓存 / 内存 / 磁盘 / 网卡)
```

六个台阶分别在这条线的位置：

| 台阶 | 打通的段落 | 建议时长 |
|---|---|---|
| 1 数据表示 | 源码 ↔ 内存里的比特 | 2~3 周 |
| 2 汇编 | 源码 ↔ 机器码 | 3~4 周 |
| 3 链接与装载 | 机器码 ↔ 进程 | 4~6 周 |
| 4 操作系统 | 进程 ↔ 内核 ↔ 硬件 | 6~10 周 |
| 5 并发与内存模型 | 多核下的正确性 | 3~4 周 |
| 6 性能 | 硬件层的瓶颈定位 | 2~3 周（可选） |

按每周 8~10 小时算，全走完约 20 周。可以砍，见「ROI 排序」。

## 台阶 1：数据在内存里怎么活着

**目标**：不再把变量当成"名字"，而是当成"某地址上的一段字节"。

**核心内容**

- 整数补码、无符号回绕、有符号溢出（UB）
- IEEE 754 浮点：为什么 `0.1 + 0.2 != 0.3`，为什么 `NaN != NaN`
- 字节序（小端）、对齐、`padding`
- 指针就是地址：数组连续、链表的节点散布、`char*` 与 `int*` 的区别只在步长
- 栈的方向（向下增长）、堆的分配粒度

**材料**

- CSAPP 第 2 章（信息的表示和处理）——只读这一章就够，别整本啃
- 想更"治愈"的可以配《编码：隐匿在计算机软硬件背后的语言》（Petzold），当睡前读物

**动手**（必须做，否则不算）

```c
// 1. 验证对齐与 padding
struct A { char a; int b; };        // 为什么是 8 不是 5
struct B { char a; char b; int c; };
printf("%zu %zu\n", sizeof(struct A), offsetof(struct A, b));

// 2. 验证浮点精度
printf("%.20f\n", 0.1 + 0.2);

// 3. 用指针走一遍数组，打印每个元素的地址差
```

```bash
# 看一个 int 在小端的字节序
xxd -g1 <(echo -n)   # 或者直接写个程序 printf("%02x", ...)
```

**验收**

- [ ] 能解释 `struct { char a; int b; }` 为什么占 8 字节，编译器在哪补了 3 字节
- [ ] 能解释 `0.1 + 0.2 == 0.3` 为假的确切原因（不是"精度问题"四个字）
- [ ] 能画出 `int arr[3]` 和 `int **p` 在内存里的布局差异
- [ ] 知道 `malloc(1)` 实际给你多少（看 `malloc_usable_size`）

## 台阶 2：汇编 = 机器码的可读文本

**目标**：看到反汇编不再是天书，能把 20 行 C 手工还原出来。

**核心内容**

- 通用寄存器与它们的"历史包袱"（`rax/eax/ax/al` 是同一个寄存器的不同宽度）
- 寻址模式：`[base + index*scale + disp]`，`lea` 是"算地址"不是"取值"
- 调用约定：x86-64 System V（Linux）前 6 个参数走 `rdi/rsi/rdx/rcx/r8/r9`；Win64 前 4 个走 `rcx/rdx/r8/r9` + **32 字节影子空间** + 16 字节栈对齐
- 栈帧：`push rbp; mov rbp, rsp; sub rsp, N` 到底在干什么
- 控制流：`cmp` + `jcc` 的组合怎么还原成 `if/for/while`
- 常见编译器"惯用法"：`xor eax, eax` = 0，`test rax, rax` = 判空

**材料**

- 王爽《汇编语言》第 3 版**前 8 章**——中文最好入门的寄存器/内存/栈教学。**读完就停**，后面的 DOS 中断调用没有现代价值
- CSAPP 第 3 章（程序的机器级表示）——主线，读两遍
- x86-64 ABI 文档（System V ABI PDF / Microsoft x64 calling convention 文档）
- [Compiler Explorer](https://godbolt.org) —— 最高效的练习场

**动手**

1. 写 10 行 C（带循环、带函数调用、带指针），在 godbolt 上对比 `-O0` 和 `-O2`，逐行标注
2. 手写一个 x64 汇编 Hello World（Linux 用 `syscall`，Windows 用 `ml64` 调 `WriteConsoleA`）
3. 用 `gdb`（或 `x64dbg`）单步，每执行一条 `push`/`pop` 就打印 `rsp`，把栈画出来
4. 手写一个递归函数（斐波那契），观察栈帧一层层叠上去

**验收**

- [ ] 给一段 20 行 `-O0` 反汇编，能说出每条指令在干什么
- [ ] 能把 `-O2` 的反汇编还原出大致 C 结构（`-O0` 太直白，`-O2` 才是真实世界）
- [ ] 能说清 Linux 和 Windows 的 x64 调用约定差在哪（寄存器数量 + 影子空间）
- [ ] 知道 `mov rax, [rbx]` 和 `lea rax, [rbx]` 的区别，以及编译器什么时候偏爱用 `lea` 做算术

> [!note] 32 位汇编在这里的位置
> 罗云彬《Windows 环境下 32 位汇编语言程序设计》**不属于主线**，它是台阶 2 的补充读物：
> - 值得读：调用约定的推导过程、**PE 文件结构那一章**（中文逆向入门最好的材料）
> - 跳过：GDI 绘图、注册表、通用控件拖拽示例、书末几万行的完整程序
> - 三个坑：MASM32 SDK 别装（用 VS 的 `ml.exe`）；`FS:[0]` 的 SEH 链表在 x64 上**不存在**（换成 `.pdata/.xdata` 表驱动）；"假设 DLL 基址固定"的示例在 ASLR 下必崩
> 结论：32 位只在需要读老样本/老软件时才用，练习请直接用 x64。

## 台阶 3：从源码到进程（性价比最高的一层）

**目标**：彻底搞懂"我 `make` 完为什么跑不起来"。

**核心内容**

- 编译四阶段：`.c → .i（预处理）→ .s（汇编文本）→ .o（目标文件）→ 可执行文件`
- ELF 结构：段（section）vs 段（segment）、`.text/.data/.bss/.rodata`、符号表、重定位表
- 静态链接 vs 动态链接：为什么静态链接的程序大 10 倍
- **PLT/GOT 与延迟绑定**：为什么第一次调 `printf` 会慢一点
- 库的 ABI 兼容：为什么改一个结构体字段就要重编所有依赖（ODR）
- 加载器：`execve` 之后内核做了什么，`ld.so` 怎么找 `.so`（`RPATH` / `LD_LIBRARY_PATH` / `/etc/ld.so.cache`）
- `LD_PRELOAD` 的原理

**材料**

- 《程序员的自我修养——链接、装载与库》（俞甲子等）——**中文唯一的好书**，也是最被低估的一本。薄，但每章都是干货
- CSAPP 第 7 章（链接）作为对照

**动手**

```bash
# 把自己写的 hello.c 完整解剖一遍
gcc -E hello.c -o hello.i      # 预处理
gcc -S hello.c -o hello.s      # 汇编
gcc -c hello.s -o hello.o      # 汇编器
gcc hello.o -o hello           # 链接（动态）
gcc -static hello.o -o hello_s # 链接（静态）—— 比一比体积

file hello; ldd hello
readelf -h -S -s -r hello      # 头、节、符号、重定位
objdump -d hello | less
nm -C hello.o
```

```bash
# 亲手写一个 .so，再用 LD_PRELOAD 劫持 malloc
# 记录每一次分配，然后跑 ls，看它分配了多久
LD_PRELOAD=./mymalloc.so ls
LD_DEBUG=libs,bindings ls 2>&1 | less
```

**验收**

- [ ] 能解释 "error while loading shared libraries: libxxx.so: cannot open shared object file" 的完整排查路径
- [ ] 能解释 `.bss` 为什么不占文件体积，`.data` 为什么占
- [ ] 能解释 `-fPIC` 和 `-fPIE` 在解决什么问题
- [ ] 能手写一个 `LD_PRELOAD` 拦截 `open()`，记录进程打开的所有文件
- [ ] 能说清 PLT 表项第一次被调用时发生了什么

## 台阶 4：操作系统

**目标**：能说清一次 `read()` 从用户态到磁盘再回来的完整路径。

**核心内容**

- 进程 vs 线程：`task_struct`、`clone()` 的几个 flag 决定了共享什么
- 调度：CFS、优先级、`nice`、CPU 亲和性
- **虚拟内存**：页表、多级页表、TLB、缺页异常、`mmap`、写时复制（COW）
- 系统调用：`syscall` 指令、参数传递、`sysenter` 的历史
- 文件系统：VFS 抽象、inode、page cache、`write` 为什么"返回了但没落盘"
- 中断与软中断：网卡收包怎么变成你的 `recv()` 返回值
- 内存分配器：`brk` vs `mmap`、glibc 的 arena、为什么 `free` 不还给系统

**材料**

- **OSTEP**（*Operating Systems: Three Easy Pieces*，[官网分章 PDF 免费](https://pages.cs.wisc.edu/~remzi/OSTEP/)）—— 最好的入门 OS 教材，比任何中文教材都好读
- **xv6 + [MIT 6.1810 实验](https://pdos.csail.mit.edu/6.1810/2026/xv6.html)**—— 只做 lab1~lab5（syscall、trap、page table、copy-on-write、thread），不用全做。2000 行级别的内核，一天能读完主体
- 偏 Windows 的话：Windows Internals 7th（进程/线程、内存管理器、I/O 管理器三部分）——**当参考书查，不要通读**

**动手**

```bash
strace -f -e trace=openat,read,write,mmap ls    # 一次 ls 的全部系统调用
cat /proc/self/maps                             # 进程地址空间长什么样
pmap <pid>                                      # 更易读的版本
ls /sys/kernel/debug/ 2>/dev/null               # 有 root 可以看更多
```

必做实验（自己写，别找答案）：

1. `LD_PRELOAD` 拦截 `open/openat`，统计一个进程访问了哪些文件
2. 写程序 `malloc` 1GB 但不写，观察 RSS 为 0（虚拟内存 vs 物理内存）
3. 写程序 `fork()` 后父子各写同一块内存，观察 COW 触发后的 RSS 变化
4. xv6 上加一个系统调用（`sys_hello`），从用户态一路调到内核

**验收**

- [ ] 能画出 `read(fd, buf, n)` 从用户态 → 内核 → page cache → 磁盘的完整路径
- [ ] 能解释为什么 `fork()` 之后立刻 `malloc` 不会复制物理页
- [ ] 能解释 `cat /proc/self/maps` 里每一行是什么（`[heap]`、`[stack]`、`[vdso]`、匿名映射）
- [ ] 能解释 `write()` 返回成功但机器断电数据丢了的原因（page cache + fsync）
- [ ] 能解释进程和线程在 Linux 内核里为什么是同一个结构体

## 台阶 5：并发与内存模型

**目标**：能解释"为什么我的程序在单核上对、多核上错"。

**核心内容**

- 缓存一致性：MESI 状态机
- 内存序：x86 的 TSO、ARM 的弱序、编译器重排 + CPU 重排
- 原子操作：`lock` 前缀、`cmpxchg`、CAS 的 ABA 问题
- 锁的实现：自旋锁、futex（Linux 上 `mutex` 的底层）、读写锁
- **伪共享**（false sharing）与缓存行填充
- 内存模型在语言层的投影：`volatile`、C11 `_Atomic`、Go 的 happens-before、Rust 的 `Ordering`

**材料**

- CSAPP 第 12 章（并发编程）
- Paul McKenney《Is Parallel Programming Hard, And, If So, What Can You Do About It?》—— [官网 PDF 免费](https://www.kernel.org/pub/linux/kernel/people/paulmck/perfbook/perfbook.html)，专治"我以为我懂内存序"
- Go / Rust 官方内存模型文档，对照着看

**动手**

```c
// 用 C11 _Atomic 写一个自旋锁，然后用它保护一个计数器
// 再写一个无锁队列（单生产者单消费者起步）
```

```bash
perf c2c record ./your_program   # 检测伪共享
perf c2c report
```

**验收**

- [ ] 能解释 `volatile` 为什么**不是**同步原语（它不保证原子性，也不保证跨核可见性顺序）
- [ ] 能解释 x86 的 TSO 相对 ARM 弱序"宽松"在哪，为什么 x86 上不加屏障的代码换到 ARM 就崩
- [ ] 能解释 `futex` 的"用户态快路径 + 内核慢路径"设计
- [ ] 能用 `perf c2c` 定位一次伪共享

## 台阶 6：性能（可选，但强烈建议做完）

**目标**：拿到一个慢程序，能说出瓶颈在哪一层。

**核心内容**

- 延迟数量级：寄存器 < 1ns，L1 ~1ns，L2 ~4ns，L3 ~15~40ns，内存 ~80~100ns，SSD ~100μs，网络 ~ms
- 缓存友好：顺序访问 vs 随机访问、AoS vs SoA、循环分块
- 分支预测与投机执行
- SIMD（SSE/AVX）与自动向量化
- NUMA、绑核
- 分析工具：`perf`、`eBPF`、VTune

**材料**

- Denis Bakhvalov《Performance Analysis and Tuning on Modern CPUs》—— [GitHub 全文免费](https://github.com/dendibakh/perf-book)，工程向
- [Agner Fog 的 instruction tables / microarchitecture 文档](https://www.agner.org/optimize/)
- CSAPP 第 5、6 章

**动手**

1. 写两个矩阵乘法（朴素 vs 分块），用 `perf stat` 对比 cache-miss 和 IPC
2. 拿自己项目里一个慢接口，用 `perf record` 出火焰图，定位热点
3. 用 `perf stat` 判断一个程序是 CPU-bound 还是 memory-bound

**验收**

- [ ] 能凭 `perf stat` 的 IPC + cache-miss 判断瓶颈层级
- [ ] 能解释为什么"遍历二维数组时先行后列"能快好几倍
- [ ] 知道什么时候值得上 SIMD，什么时候不值得

## ROI 排序与"可以不做"的清单

### 必做（按顺序）

1. 台阶 1（数据表示）—— 2 周，是后面一切的地基
2. 台阶 2（汇编，x64）—— 3 周，读反汇编的能力
3. 台阶 3（链接装载）—— 4 周，**投入产出比最高**
4. 台阶 4 的虚拟内存 + 系统调用 + page cache —— 3 周，不必学完整个 OS

### 建议做

5. 台阶 4 的调度与文件系统 —— 2 周
6. 台阶 5 的内存模型 —— 2 周
7. 台阶 6 的性能分析 —— 2 周

### 可以不做（除非真的好奇）

- **数字电路 / 逻辑门 / CPU 微架构细节** —— 想学就用 Nand2Tetris 或 Ben Eater 的 8 位机视频，纯兴趣项目，对日常排障帮助很小
- **编译原理（写编译器）** —— 除非要写 DSL，用 Crafting Interpreters 当兴趣即可
- **Linux 内核源码通读** —— 先读 xv6，2000 行；直接读内核会溺死
- **汇编语言写完整应用** —— 2026 年没有产出场景

## 避坑清单

> [!danger] 六个典型失败模式
> 1. **从数字电路开始** —— 三个月后还在画触发器，一个 bug 也没修过
> 2. **整本啃 CSAPP** —— 它是参考书，按需查章节；通读会卡在第 4 章（处理器体系结构）
> 3. **只看不写** —— 每一层都必须有可运行的产出，否则第 3 个月就忘光
> 4. **一上来读 Linux 源码** —— 容器/命名空间那块尤其劝退，先 xv6
> 5. **买课代替动手** —— 视频看完的"懂"是幻觉，`perf` 不会陪你演戏
> 6. **追求"学完再做项目"** —— 反过来：拿手上的真实问题当项目，边查边补

## 最小可行路径（时间不够时）

### 只有 10 小时

1. godbolt 上把 3 段自己的 C 代码看 `-O2` 汇编，逐行标注（3h）
2. `readelf -a` + `objdump -d` 解剖一个自己写的程序（3h）
3. `strace -f` 跟踪一次 `ls`，画出系统调用链（2h）
4. `cat /proc/self/maps` 读懂地址空间布局（2h）

### 只有 1 个月（每天 1 小时）

- 第 1 周：CSAPP 第 2、3 章 + godbolt 练习
- 第 2 周：《程序员的自我修养》前 6 章 + ELF 解剖

- 第 4 周：OSTEP 并发部分 + 手写自旋锁

## 怎么知道自己补到位了

不用"读完几本书"当标准，用**能不能回答问题**当标准：

| 现象 | 补到位后的反应 |
|---|---|
| 程序段错误 | 能根据 core dump / `dmesg` 定位到具体指针和偏移 |
| 服务变慢 | 先 `perf stat` 判断 CPU/memory/IO 哪一层，再决定加不加机器 |
| 找不到 .so | 能一路查到 `ld.so.cache`、`RPATH`、`LD_LIBRARY_PATH` 的优先级 |
| 多线程数据错乱 | 能区分是竞争、重排还是伪共享 |
| 看反汇编 | 能还原出 C 结构，认出编译器惯用法 |
| 内存涨了 | 能区分是泄漏、碎片、page cache 还是 COW 造成的 RSS 上涨 |
