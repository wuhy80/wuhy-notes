# Hermes

> [!summary] 定位
> 这里的 `Hermes` 指类似 [[OpenClaw]] 的个人常驻智能体，而不是 Nous Hermes 模型系列。它更接近“数字员工 / 个人自动化 Agent 运行时”，关注长期记忆、任务执行、技能沉淀和自我改进。

## 一、重新归类

你说的这个 Hermes 不应该放在普通 Agent SDK 里。

它应该归到：

- 个人常驻智能体
- 自动化智能体运行时
- 数字员工
- Agent OS 雏形

这类系统的目标不是让开发者写一个 Agent，而是让用户运行一个长期在线、能接入外部工具、能逐步熟悉个人工作流的智能体。

## 二、和 OpenClaw 类似在哪里

| 维度 | Hermes | [[OpenClaw]] |
|---|---|---|
| 核心定位 | 个人 / 工作流自动化智能体 | 开源个人 AI 助手 |
| 运行方式 | 长期运行，逐步适配用户任务 | 长期运行，通过聊天入口接收任务 |
| 关键能力 | 任务细化、自学习、技能沉淀 | 技能系统、聊天入口、本地上下文 |
| 更像什么 | 数字员工 | 个人智能体运行时 |

## 三、和传统框架的区别

传统框架：

- [[LangGraph]]：可控工作流图
- [[AutoGen]]：多 Agent 通信协作
- [[OpenAI Agents SDK]]：Agent SDK 抽象

Hermes / OpenClaw 这类：

- 有长期运行状态
- 有用户上下文
- 有权限和账号接入
- 有工具执行能力
- 更接近“个人操作系统上的智能层”

## 四、为什么它重要

这类智能体代表一个方向：Agent 不再只是应用里的一个功能，而可能变成个人工作流的入口。

典型能力包括：

- 处理邮件
- 维护日程
- 整理资料
- 触发代码任务
- 管理 CRM / 财务 / 内容发布
- 根据历史任务形成技能

## 五、风险

> [!warning] 核心风险
> Hermes / OpenClaw 这类智能体的风险来自“持续在线 + 高权限 + 记忆 + 可安装技能”。它们必须按半个员工来管理权限，而不是按普通聊天机器人来管理。

需要重点看：

- 是否支持权限分级
- 是否支持执行前确认
- 是否支持技能审计
- 是否能隔离敏感账号
- 是否有可回滚的执行日志
- 是否能避免长期记忆被污染

## 六、我的判断

你这个提醒是对的。  
Hermes 应该作为 Agent 目录里的一个独立方向保留，而且应该和 [[OpenClaw]] 一起代表“个人常驻智能体”这一类。

这类系统和 [[LangGraph]]、[[AutoGen]] 不冲突：前者更像运行时和产品形态，后者更像构建复杂智能流程的开发框架。
