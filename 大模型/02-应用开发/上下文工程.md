# 上下文工程

> [!summary] 一句话理解
> 提示词工程优化的是「一句话怎么说」，上下文工程设计的是「模型这一轮调用时上下文窗口里放什么」——系统提示、检索结果、工具返回、历史记忆如何检索、压缩、排序与裁剪。它是 2025 年 Agent 实践把 RAG、MCP、记忆系统统一起来的方法论框架。

## 一、为什么从提示词工程升级

单轮问答时代，提示词几乎就是全部输入。Agent 时代变了：

- 多轮长任务跑几十步，上下文会被工具返回和中间结果撑爆
- 模型有「中间迷失」现象：关键信息埋在长上下文中间时召回率下降
- KV Cache 按长度计费，塞得越多越慢越贵

于是重心从「写好那句提示词」变成「管理好整个窗口」：什么该进来、以什么形态进来、什么时候该被清出去。

## 二、四层框架（Survey 视角）

《A Survey of Context Engineering for Large Language Models》（arXiv:2507.13334）把领域切成四层：

| 层 | 回答的问题 | 典型技术 |
|------|-----------|---------|
| 检索与生成 | 信息从哪来 | RAG、记忆系统、工具调用、知识图谱 |
| 处理 | 进来之后怎么加工 | 压缩摘要、重排序、结构化（XML/JSON 分区）、长上下文自细化 |
| 管理 | 窗口预算怎么分配 | 截断策略、分层记忆（短期草稿/长期存储）、对话状态维护 |
| 系统集成 | 多组件怎么协同 | 多智能体分工、上下文在 Agent 间的传递协议 |

## 四、实操清单（做 Agent 时逐条过）

1. **稳定前缀**：系统提示放最前且保持逐字节一致，让 KV Cache 命中率最大化（和[[大模型/04-部署与工具链/本地部署/Qwen3.8-27B 显存与 KV Cache 预算|KV Cache 预算]]直接相关）
2. **结构化分区**：用明确的标签把「指令 / 检索资料 / 工具结果 / 历史」隔开，别让数据混进指令区
3. **工具结果瘦身**：MCP/RAG 返回只保留模型需要的字段，超大结果先本地裁剪再进窗口
4. **压缩而非丢弃**：多轮长任务用「滚动摘要」替换早期轮次，保留决策与结论、丢弃过程
5. **关键信息放两头**：优先级高的内容放开头（指令区）或结尾（紧邻生成位置），避开「中间迷失」区
6. **记忆分层**：会话内草稿用临时上下文，跨会话知识落外部存储（向量库/文件），用时再检索进来
